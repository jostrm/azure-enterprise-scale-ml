GitHub Actions

infrastructure-tests.yml listens for every push, pull request and manual dispatch, with no branch filter. Push is required: a local commit alone cannot launch GitHub checks.

  • IaC / unit / ubuntu-22.04
  • IaC / unit / windows-2022
  • IaC / syntax / ubuntu-22.04
  • IaC / bicep / ubuntu-22.04

Actions are pinned to immutable commits, token permission is contents: read, and checkout uses persist-credentials: false. No Azure secrets or service connection is needed, including for fork PRs subject to GitHub's approval policy.

Merge gates are a separate admin action. Add the four checks to the relevant GitHub branch ruleset. This change does not configure required checks automatically.

Azure DevOps

Create a pipeline using Existing Azure Pipelines YAML file and select environment_setup/unit-tests/test-bicep/azure-pipelines.yml.

The same unit Linux/Windows, syntax Linux and Bicep Linux jobs run through the shared run_ci.py. Python 3.12 and checksum-verified Bicep 0.44.1 are the CI tool versions.

YAML triggers cover all branches. For GitHub-backed ADO pipelines, the YAML PR trigger applies. For Azure Repos, configure a Build validation branch policy; its PR checks do not use YAML pr. Confirm the ADO UI has not overridden CI triggers.

Registering the YAML pipeline and setting branch policies are manual setup steps. No pipeline registration or cloud configuration is performed by this guide.

Local entrypoint

From the repository root, use the existing Python requirements, Bash, Git and PowerShell Core. Install an appropriate standalone Bicep compiler for your operating system; pass its executable path on Windows. The CI installer is Linux x64 only.

cd environment_setup/unit-tests/test-bicep
python -m pip install -r requirements.txt
python run_ci.py --phase unit --require-ci-tools
python run_ci.py --phase syntax
python run_bicep_matrix.py --prepare-cache --bicep bicep --report test-results/bicep-dependencies.json
python run_ci.py --phase bicep --bicep bicep

The separate prepare-cache command restores declared public AVM modules. Subsequent compilation and case binding use --no-restore and fail if cached dependencies are missing. CI forces LIVE_AZURE=0 and selects offline tests explicitly. It does not run opt-in integration tests.

Read artifacts as evidence, not certification

Which artifact answers which question?

  • unit-tests.xml: actual pytest results, failures and platform-specific skips. ADO also publishes these in its Tests view. Do not infer the unit total from this guide.
  • feature-contract-coverage.json: public ENABLE inventory, mapped contracts and explicit exceptions/default differences.
  • syntax.json: YAML, Python and Bash parse counts and failures.
  • bicep-dependencies.json: declared registry dependency preparation.
  • bicep-matrix.json: entrypoints, real compiler warnings, flags, case bindings, pair states and scope limits.
  • <phase>-summary.json: failed phases and azure_deployment_performed: false.

GitHub uploads per-phase/OS result artifacts even on failure (14-day retention). ADO publishes unit JUnit results and phase/OS artifacts on success or failure. A missing report or failed tool is not substituted with a mocked compiler pass.

Know the configuration exceptions

The contract inventory currently covers 44 public ENABLE flags: 41 mapped contracts and three explicit exceptions. Those public flags are a different inventory from the matrix's bool/string parameter occurrences.

  • ENABLE_AMPLS: missing GHA forwarding; not asserted deployable.
  • ENABLE_RETRIES: missing GHA forwarding; retries are not provisioning coverage.
  • ENABLE_AI_FACTORY_HUB: configuration intent, not a promised resource deployment.

Existing defaults are preserved, including documented ADO/GHA AML-AKS and hybrid-benefit differences. Missing GHA AKS forwarding and ADO Application Insights/Bing parameter wiring are corrected without silently changing customer defaults.

No subscription, tenant, credential, quota, resource existence, region capability, RBAC or live network dependency is validated. GREEN consumers pinned to PURPLE submodule commits are not automatically changed or deployed.

Real library, portable output

How VisualLearner produced this guide

The optional .NET generator references the actual AsomRecordsAB.VisualLearner.csproj portable net10.0 target through the externally supplied VisualLearnerProject MSBuild property. It constructs VisualLearnerNode values, runs VisualLearnerPresentation.Normalize, and exports VisualLearnerFlow values from VisualLearnerMotion.FlowAt at 128 deterministic times per cycle. The browser replays those samples; the static SVG uses a flow sampled at 2.75 seconds.

Five library phase enum slots are adapted as Ingestion = Push / PR, DataOps = Configuration, Training = Unit + syntax, Inference = Bicep matrix, and Agent = Review evidence. These are CI captions: no training, inference or agent execution occurs. Latitude/Longitude are explicitly repurposed as schematic y/x pixels; no geographic claim is made. Web/SVG rendering uses the Scout cp theme, not a copied MAUI surface or the library's own color palette.

The generator validates aggregate counts, binding types and all four states for every pair from the passed report. It exports only the needed snapshot fields, not source report paths or synthetic required-parameter values. The report's raw-byte SHA-256 identifies the input snapshot:

{{REPORT_HASH}}

Reproduce from an existing report

Requires .NET 10 SDK and a local checkout of the actual portable VisualLearner project. From the PURPLE repository root in PowerShell, set these paths for your own machine:

$visualLearnerProject = "<path-to-VisualLearner>\AsomRecordsAB.VisualLearner.csproj"
$report = "environment_setup\unit-tests\test-bicep\test-results\bicep-matrix.json"
$docs = "environment_setup\unit-tests\test-bicep\docs"
$project = "$docs\generator\VisualGuide.csproj"
dotnet run --project $project --no-restore "-p:VisualLearnerProject=$visualLearnerProject" -p:TargetFrameworks=net10.0 -- --report $report --output $docs
# If assets are missing, restore once and rerun the preceding command:
dotnet restore $project "-p:VisualLearnerProject=$visualLearnerProject" -p:TargetFrameworks=net10.0

Outputs are ci-visual-guide.html, ci-flow.svg and ci-scene.json. The same generator/template, library and report bytes produce identical outputs, with no timestamps or machine paths. Regeneration replaces these three files. Read the local HTML directly: no server, external JavaScript, fonts, fetch, Azure login, .NET installation or library checkout is required to view it.

The generator is optional tooling, not a CI dependency. Neither workflow builds it or reaches into an external repository. No VisualLearner or MAUI application source changes are needed.

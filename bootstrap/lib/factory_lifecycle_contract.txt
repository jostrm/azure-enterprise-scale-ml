AIFACTORY_LIFECYCLE_CONTRACT=1
============================

Factory teardown pipelines (ordered-project-pipelines-v1)
---------------------------------------------------------
factory_deletion_pipeline advertises this separate, Blob-only contract.
Package factory_deletion_pipeline.py beside factory_lifecycle.py in every pinned
runtime bundle. Existing scoped GHA/ADO workflow templates and authentication
bindings are reused; legacy delete-services shell scripts are not authorized by
this contract because their broad fallback/error handling is not a reviewed plan.

freeze_factory_deletion_pipeline(cloud, manifest, ownership_records, registered_projects)
is read-only and returns the deletion inventory. ownership_records are the explicit
catalog receipts (same shape as freeze_deletion_inventory/freeze_project_deletion);
manifest-embedded ownership copies are never read. Each registered project supplies project_id
(logical UUID), project_number (three-digit string), and registered_resource_ids
(exact ARM group and external project subnet/network IDs). Source, route and
configuration hashes, ownership, closure, preserved resources and the four boolean
true delete flags are frozen in that inventory. The scoped provider runner,
auth_namespace and deployment_object_id must match enrolled writer authority.
All selected project identities must be present, not inferred from RG names.

execute_factory_deletion_cohort(manifests, source_root, execution_root,
receipt_path, cloud_factory=Cloud, lock_factory=None) acquires and claims the
entire physical scope union before dispatch. Each scale-set manifest is one
configured provider pipeline run containing its ordered project resource stages.
Worker evidence binds every project's exact deleted resource IDs and the four
actual boolean flags. Capability hosts precede project-owned Search shared links,
then managed services, then network resources. Provider-managed children lacking
an independent DELETE are verified absent after their explicitly reviewed service
parent deletion, never through a blanket project RG cascade. Project RG deletion
requires the reviewed children to be absent and the group to be empty.

No common-resource teardown begins until ALL project pipelines in the submitted
cohort have verified successful provider completion and exact worker evidence.
The API must submit the complete factory cohort frozen by its catalog review;
individual lifecycle manifests do not enumerate other registered environments.
Protected/shared/bootstrap/platform/VPN resources and reusable hubs are retained;
an explicitly protected selected ID, ambiguous ownership, unmanaged dependency,
or overlapping mutable snapshots blocks rather than broadening deletion.

Factory-owned access hub (factory-owned-access-hub-v1)
------------------------------------------------------
factory_deletion_access_hub advertises this extension. An integrated access-hub
bootstrap may place its VPN gateway, Bastion, DNS resolver, private DNS zones and
private runner inside the factory's own common group. A hub-connected (external
mode) bootstrap keeps its VPN gateway in the shared hub but may still place a
Bastion Developer, which cannot traverse peering, in the factory's own common
VNet; an external-mode proof may cover a Bastion, DNS resolver or forwarding
ruleset there and never a VPN gateway. The API may then add
manifest access_hub_ownership, built only from consumed bootstrap stage records
(never names, tags or an accepted prerequisite baseline): contract, factory_id,
scaleset_id, subscription_id, mode, resource_group_ids (writable scopes),
resource_ids (exact bootstrap-created roots), factory_resource_groups (every
group the cohort deletes) and evidence (workflow_id, record_hash). The frozen
inventory binds its hash. Covered untagged resources take the core factory and
scale-set owner; a conflicting owner tag or a shared/protected/bootstrap/
platform/reusable tag blocks. Only covered virtualNetworkGateways (integrated
mode only), bastionHosts, dnsResolvers and dnsForwardingRulesets lose type
protection; connections, local network gateways, vWAN and ExpressRoute stay
protected. Every private DNS zone link, DNS forwarding
ruleset link and VNet peering in a covered group must target a VNet inside
factory_resource_groups, and any connection in such a group blocks.
The operator identity must not be attached to anything in scope. The deployment
principal may be attached only to covered common resources (the private runner
and its identity) because it executes project stages only. Common teardown runs
from the operator after the all-project barrier and deletes the covered hub and
runner closure last. ARM back-references (NIC virtualMachine, disk managedBy,
public IP ipConfiguration) name dependents, not dependencies.

Shared-hub spoke links (shared-hub-spoke-links-v1)
--------------------------------------------------
factory_deletion_shared_hub_links advertises this extension. A hub-connected
factory's bootstrap creates a hub-side VNet peering and private DNS zone (or DNS
forwarding ruleset) VNet links inside a shared connectivity hub that also serves
other factories. The API may add manifest shared_hub_links, built only from
consumed bootstrap stage records: contract, factory_id, scaleset_id,
subscription_id, hub_resource_group_ids (protected connectivity hub groups, never
a deletion scope) and links (id, type, remote_virtual_network_id; each inside a
hub group and targeting a VNet in this manifest's writable scopes) plus evidence
(workflow_id, record_hash). The frozen inventory binds its hash and lists
hub_links: the recorded links whose remote is a VNet this manifest deletes.
A live link to this factory's VNet that the records do not prove, or a recorded
link whose VNet was already gone, is listed in retained_hub_links and never
deleted. A recorded link that now targets another VNet, or a VNet that stays,
blocks. The factory side of a recorded hub peering pair may target the hub VNet
under factory-owned-access-hub-v1. After every project pipeline and the whole
common teardown of the cohort, the operator removes each frozen hub link only
when its spoke VNet is verifiably absent and the link still targets it; a link
Azure already cleared counts as removed. The hub VNet, gateways, Bastion, DNS
resolver, zones, rulesets, the hub group and every other network's links stay.
Children record deleted_hub_links and hub_unlink_complete.

Bootstrap operator teardown (bootstrap-operator-teardown-v1)
-------------------------------------------------------------
bootstrap_operator_teardown advertises this separate contract for a factory whose Full
bootstrap created its groups but that was never registered or enrolled, so it has no lease
store, route or pipeline. freeze_bootstrap_teardown(cloud, request) is read-only. The request
names the exact scopes (equal to the consumed bootstrap record's groups), the record's
created resource roots and hash, read-only hub_scopes (configured connectivity hub groups)
and protected_resource_ids that may not overlap any scope. Every resource in scope must be
tagged for exactly this factory/scale set or covered by the record; anything unowned, shared
or protected, any project resource (those need project pipelines), site links, vWAN and
ExpressRoute block. Connectivity types (VPN gateway, Bastion, DNS private resolver) pass
only when record-covered. The frozen inventory also lists the hub-side DNS zone/ruleset links
and peerings, plus this factory's own side of each hub peering, whose remote is one of this
factory's VNets; nothing else in a hub is ever touched.
execute_bootstrap_teardown(manifest, receipt_path) runs as the operator: it re-verifies
identity, the exact frozen inventory, delete permissions and that no deployment is active,
removes those exact links first, then deletes resources in dependency order with groups last,
re-verifying fresh inventory before each delete in place of leases, and writes a local
receipt. Drift before the first delete blocks; anything later requires reconciliation.

Receipts and infinite Blob leases survive uncertain dispatch, provider failure,
permission denial and incomplete teardown. Calling the same cohort with the same
execution directory observes persisted run IDs instead of redispatching. Local
receipt evidence must exactly match durable Blob receipts and accepted claims.
An uncertain dispatch without a verified run ID requires reconciliation; it is
never silently retried. Completed receipts are idempotent, and a resumed common
stage re-verifies every provider run. Source publication, clean execution-source
isolation and existing enrollment/identity authorization remain mandatory.

The aggregate receipt uses the generic cohort identity (cohort_hash over the
sorted manifest hashes, source_commit, source_ref; each child also records
manifest_revision and source_ref) plus contract, per-child remote_run {kind,
run_id}, worker_receipt, projects_succeeded and deletion_complete. The catalog
removes a factory only from a succeeded aggregate whose children carry exactly
the reviewed deletions and successful worker evidence for every project.

Native Foundry first run (identity-receipt-account-uami-instance-closure-project-v4)
---------------------------------------------------------
capabilities.native_foundry advertises the v4 executable contract, accompanied by
native_foundry_identity_producer="source-projected-project-uami-instance-v2". This is a
source capability, not live Azure acceptance or authorization. Earlier capabilities
and advertisements without the implemented producer/receipt/inventory entrypoints are not
sufficient. A declared blocker still takes precedence. Unverified source cannot
contribute a capability. No general effective-access or actor probe is required.

Read-only source-shaped ARM evidence omitted the new UAMI's VNet grant and retained
an unresolved principal reference. Therefore a cold injected first run does not
attempt to approve the dependent graph with a hypothetical principal. Preparation
first projects the exact compiled-v2 foundation symbols projectResourceGroup,
namingConvention and miForPrj, verifies the nested canonical naming and mi.bicep
modules, and retains only the managedIdentity leaf of mi.bicep. Its Cognitive
Services User assignment is excluded. Existing-only naming resource declarations
are reads, not writes. miPrjExists must be explicitly false. Template-spec variants,
changed source selectors, extra leaves or ambiguous scope/what-if evidence block.
The complete requested parameters/source/configuration remain bound, unchanged.

deployment.foundry_identity_stage freezes only the minimal source payload hash,
exact UAMI/RG IDs, source-declared Create/NoChange changes, pre-existing group
resource fingerprints and a binding hash of source, configuration, target,
operator/deployment identities, route, coordination and all complete source steps.
The approval_purpose is identity-only; continuation_requires_new_approval is true.
No Foundry account, model, role or persona access is executed in this stage.
The worker rechecks the source projection, preview, absence and ownership.
After persisting intent it rereads the exact initial group/resource inventory and
UAMI absence, then freshly authorizes the active claim and lease before its single
PUT. It validates actual output-bound GUID/client/tenant/ownership and exact closure.
The receipt retains the initial snapshot and final identity-only closure. Existing
resources and the existing group cannot change. Completion repeats that closure
check and authorization; failures retain reconciliation evidence without retry.

A producer worker success receipt has completion="identity-only",
continuation_required=true, only the foundry-identity-producer deployment and the
exact UAMI/RG ownership rows. foundry_identity_receipt binds the original run and
manifest, payload and configuration/source context hashes, output-bound resource
IDs, real identity metadata/body hash, observed_at, role_writes=[] and
full_project_executed=false. It is not full project success. Catalog registration
records this ownership but does not mark project/factory deployment configured.
The worker proof also records producer_prepared_at and request_hash, binding source,
configuration, target, identities, route and locks before generated step parameters.
foundry_identity_preparation reads the exact ownership-linked durable receipt and
fresh identity body to recover only the original run/time inputs. Catalog bootstrap
projection reuses these inputs instead of generating different deploymentId/random
values during the second preparation. This is not a dependent-plan approval:
the complete rebuilt source/parameter context must still match at native freezing.

Only a NEW preparation/run and separate approval can continue. Preparation reads
the producer worker receipt from the enrolled durable store using exact recorded
run_id/receipt_hash ownership, requires the same source/configuration/target/route/
coordination context, and re-observes the exact identity instance. The next review
must start within one hour of producer observation; expired or mismatched receipts
require reconciliation, never automatic recreation, refresh or a new grant.
deployment.foundry_identity_continuation binds that immutable receipt. Only the
source-selected project-UAMI lookup and producer outputs are replaced with its
validated literals. The already-produced identity leaf is omitted from the full
foundation payload; its source Cognitive Services User role remains, with the
literal principal. Canonical passwordless spAndMiArray outputs become the exact
MI-only literal array, preserving source VNet role names. A secret-backed SP array
is unsupported by this continuation; it is not read or silently discarded.
No unrelated or arbitrary future identity receives this treatment.
Catalog prepare/review can freeze this identity-only stage without a global
full-project preflight-ready assertion. Preflight availability is not a receipt.
Verified catalog jobs expose completion="identity-only", continuation_required=true.
Creation workflows retain that completed producer child without marking the
project-deployment stage complete. Any former whole-workflow authorization is
retained as invalidated history; the automatic runner stops. The same project
stage requires a fresh catalog freeze and new explicit approval, and any remaining
workflow stages also require explicit reviews rather than inheriting retired consent.
plan_foundry_lifecycle expands one exact deploy-project manifest's
non-AVM, non-CMK 09-ai-foundry-2025-v4 entrypoint into prerequisites, account-only,
and full-project phases. All parameters except foundryV22AccountOnly are retained:
existence flags, project configuration and every selected model are not rewritten.
The account-only source does not deploy models; the full phase deploys them once.
Explicit existing-account and disabled Foundry selections retain their old path.
Standalone account-only, unresolved selections and unsupported topologies block.
Resource-level Defender enabled without subscription-level Defender is rejected
before expansion because its account-only dependency is unordered. Opaque persona
writes are also blocked: they have no complete phase-specific instance/write proof.
Neither guard rewrites the user's saved parameters.

After identity production, freeze_deployment_plan reviews the complete combined graph and each cumulative
phase using ARM what-if. Exact account absence and the single new Cognitive
account in the account-phase difference bind the future output, not an account
name-prefix search. Missing, ignored, unresolved, destructive or out-of-scope
what-if evidence remains blocked. Frozen phase metadata and exact network grant
scopes are included in the reviewed manifest; phase-specific preview hashes do
not authorize changes outside its declared after-state. At execution each phase's
current preview is compared to reviewed payload hashes and preceding postconditions.
No broad stripping of runtime differences or guessed equivalence is permitted.
Exact initial inventory and all three phase-specific provider closure observations
are retained and re-read before continuation. They bind actual generated identities and
unchanged resources, not guessed pre-deployment principal IDs. Ignore/NoChange may
use only those exact observed instances; new/modified after-payloads still require
the reviewed desired hash. An observed hash may supersede a bootstrap-owned
original only after an explicit reviewed Modify with that original before-hash
in an actually executed phase write. A cumulative prior preview alone is never
write evidence. Each phase retains executed_changes, resources and closure_hash;
unchanged resources remain byte-hash identical across the complete history.
Preserve-only resources and descendants never
gain that permission. Original snapshots and their ownership proofs stay unchanged.
Native phases separately retain source_changes, the exact raw ARM change type for
each normalized resource ID. Ignore may normalize to NoChange for preservation,
but never qualifies a source-declared UAMI grant. The phase provenance is bound to
the frozen manifest and required by validation. Live provenance is checked again
during initial previews and immediately before the prerequisite root PUT; genuine
source-reasserted NoChange grants still allow exact GET payload verification.

The same enrolled provider worker and durable claim execute separate ARM root
deployments. For injection, the exact single UAMI selected by the reviewed account
identity payload is bound to 01-foundation's actual MI-name/resource-group outputs
and 09's getProjectMIPrincipalId source selector. Before the account deployment,
the worker checks the completed foundation deployment, materialized UAMI principal,
client and tenant IDs, VNet/subnet readiness and exact source-reviewed VNet Network
Contributor assignment. A UAMI GET does not invent a provisioningState when that
API omits it; producer completion and materialized identifiers are recorded instead.
Existing UAMI principal/client/tenant bindings cannot change after preparation.

There are no ad-hoc Network Contributor PUTs, no added SAMI grants and no invented
subnet grant. Source 08b-rbac-common-rg/vnetRBACReader assignments remain part of
the original reviewed ARM phases. Each phase checks preservation before writes;
unchanged preserved networks may be read but missing grants below them cannot be
created. Missing/unresolved resource IDs or grant payloads block preparation.
A candidate grant must occur in the prerequisite source what-if, including a
source-reasserted NoChange assignment. An existing bootstrap grant outside that
graph cannot substitute for the declared assignment or become a second candidate.
All other source roles, including mi.bicep's RG-scoped Cognitive Services User
assignment, remain in the complete cumulative previews and phase observations.
The receipt-bound continuation additionally freezes identity_dependent_grants,
requires the Cognitive Services User grant and exact literal project principal,
and retains source-declaration provenance. Raw Ignore is never a declaration,
including for that grant. planned-create agent identities are rejected: producing
the identity, observing it and separately reviewing concrete dependent changes is
mandatory. Every continuation phase rereads the durable producer receipt and exact
identity body before its write; full success includes the bound receipt reference.
Offline source compilation and state-machine tests are not real-cloud execution.

After the account phase, exact aiFoundryV2ResourceId/aiFoundryV2Name outputs, account
SAMI/tenant, owner, region, injection subnet and attached UAMI principal/client are
checked. The exact account capability host must reach Succeeded. Its provider proof names
the configured UAMI and hashes the earlier identity/grant observations; it never
credits subsequently added SAMI roles. Identity/grant drift is checked again before
the full-continuation boundary. Foreign scopes, wrong subjects, conditional
or delegated grants, incomplete observations and authorization errors fail closed.
Role visibility is explicitly observation, not effective-permission proof.
Provider readiness is evidence for the account's configured UAMI/network setup,
not an independent effective-access test for that principal or a runtime agent test.
The capability-host response does not identify the operation actor. Naming the
configured UAMI in a receipt therefore does not independently prove which identity
performed injection, or prove general RBAC propagation for that identity. Those
limitations are explicit false fields, not an independent actor-probe requirement.
For injected accounts the proof status is provider-ready and the required gates are
account-identity and configured-agent-network-ready. Both receipt validators require
the complete exact source/identity/grant/configuration-bound provider proof before
full continuation. The live host ID/state/body is rechecked immediately before the
full root PUT. Missing, changed or overstated evidence cannot be replaced by a
claimed successful phase. Account/provider failures retain reconciliation state
without automatic replay. No impersonation, additional probe resources, identity
attachment or unadvertised permission API is required or used.
The account's existing reviewed source dependency on subnetDelegationAca orders
delegation before account creation; no extra internal subnet phase is required.
Explicit empty aca2SubnetId follows the source's no-injection branch without
changing configuration flags. CMK/key-vault sequencing remains unsupported.

Readiness polls are bounded to 180 attempts at five-second intervals; deployments
are bounded to 1440 attempts. Every poll checks lease/claim ownership, and every
write rechecks authorization. No failed write is retried. Pending deployment/gate,
completed phases, exact identity, grant and capability-host hashes are persisted.
Each phase persists its pending intent, rechecks required identity/readiness and
the complete current instance inventory, then freshly authorizes immediately
before ARM PUT. Final success binds the last phase's exact closure to the final
inventory and ownership rows, including resource types, API versions and etags.
Completion rechecks readiness, the same complete closure and active authorization.
Missing initial evidence, truncated phase history or differing final ownership
cannot be accepted as a successful v4 receipt.
Expired review windows reject new claims; an already accepted, still-active durable
claim retains the existing continuation semantics beyond its admission deadline.
Any failure/interruption keeps reconciliation-required evidence and the durable
claim; no suffix phase or automatic account replay is allowed. Success requires
ordered phase/readiness receipts plus the unchanged final ownership closure.
Identity-only success cannot be substituted for any full phase/readiness receipt.
Local source/state-machine acceptance does not establish live provider success.
Publication, helper hashing, clean immutable source and user review remain required.

foundry_lifecycle.principal_binding is the closed source-enforced symbolic binding
for the account system identity only (foundry-account-system-identity-v1). It names
the source commit, canonical template/module/resource, producer phase/step, exact
resource ID/name output paths, the frozen account_resource_id field, principal and
tenant property paths, API version, tenant/subscription and required gate IDs in
order before the full-project step. Account identity.tenantId must match the target.
foundry_readiness records principal_binding_hash and completed_gates alongside the
exact resolved account ID, principal GUID and observation hashes. Missing gate or
binding evidence rejects continuation and success. A source dependency alone is
not this binding. Injection also requires agent_identity_binding
(foundry-source-project-uami-v1), naming its source selector, producer outputs,
properties.principalId/clientId/tenantId, required grant source, API and before-account
ordering. Frozen account/grant payload hashes bind the selected UAMI and candidate
grant IDs; foundry_agent_readiness records exact observed subject and grant hashes.
Neither these bindings nor generic properties.principalId references certify other
identities. Obsolete v1 SAMI-grant and v2 cold-preview contracts are not v3 support.

Opt-in single-writer coordination (provider-repository-cas-v1)
-----------------------------------------------------------
Blob coordination remains the default. Enrollment options may explicitly select
coordination_mode="single-writer". This is NOT an automatic fallback from Blob
errors and cannot be selected with environment variables. Blob account/container,
storage-mode and public-network options are rejected in this mode.

The reviewed plan and successful enrollment result expose these warnings:
  Bypassing lock, due to issues, dont do parallell updates on same AI Factory
  Do not make concurrent changes to a shared hub, including from other
  repositories; repository claims do not provide global exclusion.
The existing exclusive-writer governance acknowledgment must be explicitly
reviewed and supplied. No storage account, container, Storage data role, or
storage-audience token is read, created or required by this backend.

RuntimeBinding.locks for this mode is the closed object:
  {"provider":"provider-repository-cas","coordination_mode":"single-writer",
   "repository":"<exact route repository URL>",
   "state_ref":"refs/heads/aifactory-state/single-writer-v1",
   "coordination_hash":"<SHA256 of enrollment>","revision":<positive integer>}
The manifest adds scopes and common_dependencies only; inherited_leases and
Blob coordinates are forbidden. The protected envelope still uses lease_context
as the wire name, but its values bind a persistent repository claim, NOT leases.
Its mode comes only from the reviewed manifest and binding.

State lives in state.json on the dedicated deterministic state ref, never in a
consumer worktree. GitHub creates immutable blobs, trees and commits parented
by the previously read ref, then creates the absent ref or advances it with
force:false. Concurrent siblings cannot fast-forward over each other. ADO
pushes commit changes with refUpdates.oldObjectId compare-and-swap. Both
providers verify the ref and contents after each write. There is no reset,
overwrite, fallback, force-push or write retry on contention/uncertain response.
Private GitHub repositories / private ADO projects are mandatory and checked;
the helper never changes visibility. State contains enrollment, one repo-wide
active claim, run consent proofs, worker receipts and resource ownership
evidence, NOT configuration, ARM payloads, access tokens or secret values.
State is bounded to 8 MiB; reaching that bound blocks rather than discarding
receipts. Enrollment provisioning itself first reserves a persistent claim;
partial/uncertain enrollment or run results retain that claim for independent
reconciliation. Replanning or resubmitting does not clear it.

One writer_id, auth namespace, deployment identity and runner is designated for
the entire repository. Additional exact owned scopes may be enrolled add-only;
common dependencies must already have same-repository enrollment. Source,
frozen changes, current ownership, deployment identity, enrollment hash/revision,
run uniqueness and acceptance-before-expiry checks still apply. A worker reads
the same durable claim/receipts independently; envelope assertions alone are
not proof. Repository admins/code writers are trusted and can bypass/delete
this state. This does not fence other repositories or arbitrary Azure writers.

Supported: frozen common/create-factory/create-scaleset and exact project
deployments via GHA and ADO Linux workers. Single-writer deletion supports
whole-owned-group plans/cohorts only: every group and resource in the deletion
manifest must be marked delete. Mixed delete/retain and selective project
deletion are not supported by that path. It uses repository CAS, not physical
leases; legacy project pipelines remain outside this coordination contract.
This generic whole-owned-group support does not satisfy the named API's separate
ordered-project-pipelines-v1 requirement. Named deletion remains unsupported
under single-writer coordination on the API's current immutable runtime pin.
The named capability alone cannot unblock a preview or authorize a fallback.
Capabilities advertises single_writer_deletion="provider-repository-cas-cohort-v1",
coordination_modes
["blob","single-writer"], single_writer="provider-repository-cas-v1" and the
single_writer_operations list.

Publish the separately reviewed factory-lifecycle-single-writer-gha.yml or
factory-lifecycle-single-writer-ado.yml to the usual lifecycle workflow path.
Blob templates keep their existing permissions. The GHA single-writer template
alone grants contents:write and exposes github.token as GH_TOKEN only to the
worker step; its Azure login uses the enrolled environment AZURE_CLIENT_ID,
AZURE_TENANT_ID and AZURE_SUBSCRIPTION_ID variables. Local enrollment uses the
existing authenticated gh API wrapper; local lifecycle uses gh auth token.
The ADO worker exposes System.AccessToken only as AIFACTORY_STATE_TOKEN on the
worker task, with persistCredentials:false. Grant that build identity read,
create-branch and contribute access on this exact repository/state ref through
normal operator governance. Local ADO enrollment uses its explicitly selected
ADO-tenant cached CLI account; lifecycle uses the existing ADO audience wrapper.
Denied authentication/ref policy or missing build permissions fail closed.
No broader Azure IAM is added. Pin provider_repository_state.py alongside the
lifecycle/enrollment source and selected template in the reviewed source bundle.

----------
python -B bootstrap/lib/factory_lifecycle.py capabilities
python -B bootstrap/lib/factory_lifecycle.py inspect --stdin-manifest
python -B bootstrap/lib/factory_lifecycle.py execute --stdin-manifest \
  --source-root <separate-clean-published-checkout> \
  --execution-root <new-isolated-directory> --receipt <directory/receipt.json>

bootstrap/AIFactory-lifecycle.sh is the equivalent shell wrapper.
bootstrap/ADO-azurefactory.sh and bootstrap/GHA-azurefactory.sh expose inspect
and execute with the reviewed route fixed to ado or gha respectively. They
accept the same protected input and execution options. A route mismatch blocks
before authentication or execution; neither script initializes register storage.
New configuration uses the authenticated catalog UI/API create-factory
prepare/confirm flow. Legacy copy registration uses action=migrate with an
explicit source_folder and separate empty azurefactory destination.
Backend code may import validate_manifest, manifest_digest, capabilities,
execute and execute_cohort. Validation/inspect is local only and never implies Azure readiness.
There is no cloud "prepare" command: catalog/backend owns preview, frozen
configuration, published-version resolution, revisions and reconciliation.

Registered-target enrollment (separate from lifecycle execution)
---------------------------------------------------------------
ADO-azurefactory.sh, GHA-azurefactory.sh, ADO-create-new-aifactory-scaleset.sh
and GHA-create-new-aifactory-scaleset.sh all expose:
  enroll plan --consumer-root <repository> --factory-id <UUID> \
    --scale-set-id <UUID> --environment dev|stage|prod --options <nonsecret.json>
  enroll ensure <same scope/options> --expected-plan <approved-plan_hash> --yes
The optional --acknowledge-exclusive-writer-governance flag must reflect a real
administrator attestation and match the reviewed plan; it is never automatic.
ALL-create-new-aifactory-scaleset.sh --orchestrator ado|gha enroll ... selects
the same provider-pinned entrypoint. Run enroll plan|ensure --help for flags.
The thin factory_enrollment_entry.py adapter checks the provider on the same
core.load_request result passed to plan/ensure; fresh-request checks reject
consumer changes. Enrollment dispatch precedes legacy guards, but it does not
permit raw legacy options on a registered root.

Canonical factory_enrollment.py is stdlib-only and schema-2 registered-consumer
only. It has no env/active-account/legacy target fallback. Plan is cloud/provider
read-only. Ensure adds missing explicitly scoped identity, federation, role and
lock/enrollment prerequisites; contradictory existing resources fail closed.
No VM creation, agent registration, implicit RG adoption, reset, delete, lease
break, credential persistence or consumer binding write is performed.
Governance is not inferred from lock blob existence. Incomplete governance or
rights returns incomplete/blocked rather than falsely marking runtime ready.

Installed CLI equivalents:
  azurefactory enrollment plan <scope/options> --save-plan <new-plan.json>
  azurefactory enrollment ensure --plan <plan.json> --yes \
    --save-result <new-result.json>
Repeat the governance flag on both commands only when actually attested.
CLI plan artifacts bind schema/digest, request, absolute consumer path, register
reference hash and review. Ensure checks those plus fresh live state; there is
no auto-replan/approve. Artifacts never overwrite existing files. Checksums are
integrity checks, not signed approvals.
  azurefactory enrollment prepare-binding --result <result.json> \
    --expected-revision <catalog-source_revision> --save-receipt <new-receipt.json>
  azurefactory catalog confirm --receipt <receipt.json> --yes
azurefactory enrollment publish --receipt <receipt.json> --yes is the binding-only alias.
Publication always uses catalog prepare/confirm configure-binding and requires
a separately reviewed API receipt for the exact binding/factory/revision.
Enrollment readiness is not deployed-resource readiness. Runtime still performs
live validation. Ordinary source/legacy creation cannot enroll an unregistered
target: API registration, enrollment and binding publication remain separate.

Control-bundle copy/snapshot/restore includes the canonical core and adapter,
runner-prerequisites.ps1/.sh and runner-registration.ps1/.sh. Agent registration
credentials are distinct from the Azure deployment managed identity. CLI wheel
and sdist builds vendor the canonical core automatically for use outside source.

Lifecycle protected-manifest input
----------------------------------
Only a protected child stdin pipe or --protected-manifest <file.dpapi> is
accepted. The DPAPI file contains the manifest JSON itself, encrypted for the
current Windows user, without additional entropy or a wrapper envelope.
Never use shell interpolation, JSON command arguments, environment-based
configuration, or redirected plaintext manifest files. stdin MUST be created
by the trusted backend; the runtime cannot distinguish an inherited pipe from
a redirected file. Configuration is never written to the execution directory.
A successfully consumed .dpapi artifact is removed; failures retain it for
backend reconciliation. The backend owns the independent protected catalog.

Output is bounded non-secret JSON; exit 0 means successful inspection or
verified execution, exit 2 means blocked/reconciliation required. CLI stderr,
tokens, cloud error bodies and raw configuration are not passed through.
Canonical JSON: UTF-8, sorted keys, no whitespace, ensure_ascii=False,
nonfinite floats prohibited. Duplicate JSON object keys are rejected.

Frozen manifest schema
----------------------
schema: 1
operation: create-factory | create-scaleset | deploy-project | delete
run_id: UUID (one shot; never automatically retry)
manifest_revision: positive integer
prepared_at / expires_at: timezone-aware ISO timestamps, lifetime <= 3600 sec
manifest_hash: SHA256(canonical JSON of all fields EXCEPT manifest_hash)
source:
  commit: exact lower-case 40-hex published vendor commit
  ref: refs/tags/<published tag> or refs/heads/<published release>
  version: displayed published version
target:
  factory_id / scaleset_id: explicit logical IDs
  factory_type: ai (optional for legacy manifests; other factory types are blocked)
  environment: dev | stage | prod
  tenant_id / subscription_id: exact GUIDs
  prefix / region / suffix: exact naming; suffix three digits, not 000
  project_ids: explicit three-digit IDs; [] is valid for zero-project creation
identity:
  object_id: exact authenticated Azure principal object GUID
  deployment_object_id: exact CI deployment principal GUID (scoped plans only)
route:
  kind: gha | ado
  writer_id: designated writer enrollment key
  repository: credential-free https GitHub or dev.azure.com repository URL
  ref / commit: exact consumer ref and reviewed 40-hex commit
  shared_remote: explicit boolean
  scoped_contract: 1 (required for scoped GHA/ADO deployment plans)
  auth_namespace: unique GitHub environment / ADO service-connection name
  github_user_id: exact authenticated GitHub numeric account ID (GHA only)
  runner: explicit scoped runner selection:
    {kind: hosted, os: linux, image: ubuntu-latest|ubuntu-24.04|ubuntu-22.04}
    or GHA {kind: self-hosted, os: linux, labels: [self-hosted,linux,<label>]}
    or ADO {kind: self-hosted, os: linux, pool: <pool>, agent_name: <optional>}
config: complete resolved selected deployment object, never catalog settings
locks:
  provider: azure-blob-lease
  account_url: https://<account>.blob.core.windows.net
  container / coordination_blob: operator-provisioned enrollment destination
  coordination_hash: SHA256(canonical enrollment JSON)
  revision: enrollment revision
  scopes: nonempty explicit physical resource-group ARM IDs in target subscription
  common_dependencies: all other physical common/dependency RG ARM IDs
  inherited_leases: optional {lowercase_physical_rg_id: preselected_lease_UUID}

deploy-project requires one project ID. Its exact dev or stage_prod section
must contain matching tenantId, dev_sub_id/test_sub_id/prod_sub_id,
project_number_000, admin_location, admin_aifactoryPrefixRG and
admin_aifactorySuffixRG (dash plus suffix). No Dev fallback, destructive
deployment flags, automatic template update, commit/push or settings overwrite.

Deletion adds:
deletion:
  inventory_complete: true
  revision: same as manifest_revision
  inventory_hash: SHA256(canonical resources array)
  resources:
    - id / type / api_version: exact audited ARM leaf identity
      etag: observed ETag or null when provider has none
      body_hash: SHA256(canonical full ARM GET response body)
      owner: factory_id, scaleset_id, optional project_id
      depends_on: explicit resource IDs in this inventory
      delete: explicit boolean
  resource_groups:
    - id: one entry for every locks.scopes resource group
      etag: observed ETag or null
      body_hash: SHA256(canonical full resource-group GET response body)
      delete: false for leaf deletion; true for complete owned-group deletion

Ownership comes from actual resource tags aifactory.factory_id,
aifactory.scaleset_id and, for projects, aifactory.project_id. Name/prefix is
NEVER evidence of ownership. Unknown, unowned, changed, duplicate, nested,
unlisted and unsupported resources block. Resource listing is fully paged,
bounded, then compared with the exact allowlist; full resource fingerprints
and ownership are re-read under leases before EACH mutation. Retained
resources cannot depend on deleted resources. Deletion is reverse dependency
order and verifies each exact resource GET returns 404 before advancing.
No subscription, repository or external hub DELETE is issued. Resource-group
DELETE requires the complete owned-group contract below, never a prefix match.
At least one explicitly authorized deletion is required; an empty allowlist
does not produce a success-shaped no-op. Active or queued GHA/ADO runs in all
enrolled target/dependency repositories are checked, as are active ARM
deployments. GHA enrollment requires an existing authenticated gh CLI session
for read-only run inventory, even when deletion itself uses Azure directly.
Unreadable or incomplete run inventory blocks. Repository-wide checking is
deliberately conservative: unrelated active runs in that repository also block.

Required operator setup (runtime NEVER provisions this implicitly)
----------------------------------------------------------------
1. Provision a dedicated Azure Storage account/container, Microsoft Entra
   data-plane access, and the enrollment JSON below. Public Azure endpoints
   only are currently supported. Do not store configuration or credentials
   in this container.
2. Precreate a zero-byte blob for EVERY physical RG and common dependency:
     locks/<SHA256(UTF-8 lowercase full ARM RG ID)>.lock
   All environments, users, machines, GHA and ADO writers MUST use this exact
   account/container/key algorithm. Factory ID, project ID, orchestrator,
   run UUID, local workspace and catalog paths MUST NOT partition lock keys.
3. Establish one designated writer per target. Prevent manual/legacy
   deployment routes from bypassing the lease protocol through operational
   permissions and orchestration governance. Enrollment is an administrator
   attestation of actual enforcement, NOT a toggle making legacy workflows
   magically safe. If this cannot be established, do not enroll the target.
4. Pin this enrollment's hash and revision into each protected prepared run.
   The enrollment must list all common dependencies and their enrolled
   writers; configuration-only self-assertions are not sufficient.

Locks use real Azure Blob infinite exclusive leases, checked before every
mutation. Infinite leases deliberately fail closed on process/machine death:
they cannot expire while a remote pipeline or ARM DELETE remains in flight.
No local mutex substitutes for them. Sorted acquisition prevents deadlock;
partial acquisition releases already acquired leases. The conditional blob
create runs/<run_id>.json (If-None-Match: *) provides cross-machine replay
protection. Receipts, not secrets, are persisted there and atomically locally.

Consent is required to be current WHEN CLAIMED, not throughout execution.
validate_manifest(document) remains strict for new/unclaimed input; its optional
now argument is an inspection/test aid and is NOT accepted by execute or
execute_cohort. Neither root execution API accepts approval timestamps,
skip-expiry flags or caller-provided execution authorization.
After verified leases are held, claim_run validates the entire frozen manifest
and current lifetime, conditionally creates runs/<run_id>.json and the immutable
runs/<run_id>.claim.json, and verifies consent is still current after persistence.
The claim contains schema, generated claim_id, run_id, manifest_hash, exact
source, runtime-generated accepted_at and SHA256(canonical lease context).
The mutable receipt preserves this evidence as execution_claim. These records
are non-secret; actual lease UUIDs remain in protected transport only.

Only an internal frozen execution-claim value permits post-deadline execution.
It revalidates immutable manifest content, live immutable claim, active parent
record, exact original lease-context hash, live physical leases and enrollment.
Changing and rehashing the manifest after claiming is rejected. No prepared_at
or expires_at is rewritten. A bare success dictionary, local claim, or timestamp
echo cannot grant continued authority. Storage write access is a trusted
operator/runtime prerequisite, not a user-controlled approval input: govern
claim/receipt writers and prevent out-of-protocol changes.

On uncertain dispatch, timeout, exception after a possible mutation, or
partial deletion, leases and receipts remain. No blind retry or success.
An operator/backend must inspect the exact remote run/resource inventory,
record reconciliation and explicitly break retained leases before preparing
a fresh revision/run UUID. Never break a lease while an old mutation can
still run. A secretless terminal receipt is retained after successful release.
Deletion identity is bound to subscription, tenant and token oid; no login,
subscription switch or credential fallback occurs. Source validation is
read-only: clean tracked tree, exact HEAD, trusted vendor origin and published
ref resolving to exact commit. Consumer files are never touched.

Add this fully frozen deployment object to a create-factory, create-scaleset

  deployment:

-----------------------------------------------------
For commonNetworkProfile=preserve-v1, the network12 step MUST carry
network_preservation with contract=preserve-v1-runtime-proof, the exact
source_payload_sha256, desired network parameters/IDs from successful native
foundation, and expected_resource_ids from its verified postflight.
The only permitted replay has createVnet=false and empty createSubnets and
createNetworkSecurityGroups. The published helper validates actual compiled
ARM semantics and exact parameters, not a BYO flag or profile-name assertion.
Preparation freezes a NEW snapshot_sha256 after runner/private-endpoint setup.
The worker recollects the exact network footprint under its held lease and
rejects changed configuration, etags, compiler output or source before PUT.
This proves only network12's zero-write footprint; it does not certify
13-rgLevel, arbitrary DNS operations or later project effects.

For groups actually created by the reviewed native minimum stage, the backend
may attach deployment.bootstrap_foundation with
contract=created-group-ownership-v1 and groups={lowercase_RG_ID:
{plan_id: native_creation_UUID, plan_hash: approved_native_plan_SHA256}}.
Reused/shared groups are not creation claims. Preparation freezes
bootstrap_ownership entries for untagged descendants of those exact locked,
ownership-tagged groups; each entry binds owner and current body_hash.
The worker verifies those snapshots again under the lease before mutation.
Foreign ownership and changed instances block. The backend stops attaching
each group's bootstrap claim once ordinary lifecycle ownership is recorded.
This handoff avoids requiring a prior lifecycle receipt before the first
workload without treating unrelated groups as adoptable.

Pure parameter preparation utility:
  resolve_template_parameters(compiled_template, selected_values, parameter_sources)
Explicit parameter_sources maps Bicep parameter names to selected config keys.
The utility resolves only literal published defaults, converts declared scalar
types, and returns parameters, consumed_configuration_keys,
unused_configuration_keys and published_defaults. It never defaults identity
fields/project numbers or credentials, and never evaluates unresolved ARM
default expressions. Backend must account for unused deployment settings or
block preparation; unused keys are not silently discarded. Execution still
requires the complete frozen parameter object.

Each combined change is:
  resource_id: exact ARM ID in locked writable resource groups
  change_type: Create | Modify | NoChange
  before_hash: SHA256(canonical before body), or null when absent
  after_hash: SHA256(canonical after body), or null when absent
Delete, Ignore/unsupported, incomplete expansion and out-of-scope changes
block. The worker repeats the complete combined what-if under the same
physical leases and compares it exactly before mutation.

All selected phases are combined into one subscription-scoped ARM deployment
with explicit nested dependencies and secureObject parameter envelopes. This
lets ARM preview and deploy the common/project dependency graph together;
it does not compare later phases against an obsolete pre-foundation state.
Every child deployment is individually verified after the parent succeeds.
Plans larger than ARM's 4-MiB inline template limit must use prepublished
Template Spec versions. Each linked specification is re-read, must exactly
match the frozen compiled template hash, and its artifact RG must be included
in the common physical lease dependencies. No template publishing or SAS
creation is performed by this runner.

Additional enrollment writer fields:
  auth_namespace: exact route.auth_namespace
  deployment_object_id: exact identity.deployment_object_id
  runner: exact route.runner descriptor
No two writers in the same remote/kind may share an auth namespace. Both the
operator and CI principal need the appropriate Azure Storage lease/receipt
permissions; the worker verifies the CI principal rather than impersonating
the operator. Namespaced environment/service-connection credentials are
preprovisioned. The adapter never overwrites shared root variables or auth.
New scoped templates support Linux hosted/private self-hosted workers with
Python 3, Git, Azure CLI and the reviewed Bicep executable installed on PATH.
The new profiles explicitly use that executable, not a downloaded/default
compiler from somebody else's Azure CLI profile. Windows
CI workers are an explicit capability blocker, not silently replaced with
Ubuntu. Frozen useSelfHostedBuildAgent, runner label/pool/name and BYO_subnets
choices are checked against route.runner and deployment.network_mode.
Existing untagged resources require known_ownership evidence matching their
current full fingerprint before any update. This prevents silently adopting
a different resource instance at a recycled ID. Successful updates carry the
verified owner forward into a newly fingerprinted worker receipt.

GHA dispatch creates a unique create-only refs/tags/aifactory-runs/<run_id>
at the frozen consumer commit. No main/consumer branch or tracked file is
changed. The new workflow checks workflow_sha AND event SHA before Azure
authentication, checks the checked-out consumer and vendor commits, and
executes only the protected manifest. Runtime correlates the UUID run title
and exact commit. Up to sixteen 32,000-character encrypted run-specific
environment-secret chunks carry a zlib-compressed, base64 manifest/lease
envelope; decompression is strictly bounded to 8 MiB. Larger compressed
payloads block explicitly. Confirmed terminal runs remove these chunks and
the unchanged run tag. Uncertain dispatch retains them for reconciliation.

ADO uses exact resources.repositories.self.version, a namespaced reviewed
workload-identity-federation service connection and one per-run secret envelope variable. Its template
checks consumer/source commits before the AzureCLI task authenticates.
Both routes execute the same worker via private stdin; no configuration or
lease secret is placed in command arguments, shell text, logs or local files.
ADO encrypted variable history remains governed by ADO retention.
GHA uses a new private, run/attempt-specific Azure CLI profile under its
ephemeral checkout and removes only that profile in an always-cleanup step.
ADO explicitly disables global Azure CLI configuration. The worker verifies
that the connection's selected account itself matches the frozen target;
it does not silently compensate for a misbound environment/service connection.
Long-running GHA workers renew the same federated identity through the trusted
GitHub OIDC endpoint and Entra token endpoint, in memory and without assertions
in argv. Issuer, audience, repository, run, tag, commit and environment subject
are checked before exchange; returned Azure tenant/principal are checked too.
ADO requires a current AzureCLI@2 task supporting keepAzSessionActive for WIF,
enabled by the new template. It refreshes the same isolated connection rather
than retrying deployments or falling back to another credential.

The worker shares the coordinator's existing permanent physical leases; it
cannot reacquire or bypass them. Before accepting even an unexpired envelope it
reads the parent's immutable claim and active record from the authoritative
store, verifies the frozen hash/source and live lease context, and rejects missing,
terminal, changed or replayed authority. Thus a correctly accepted queued job
may start after consent expiry without trusting timestamps in its envelope.
It checks the exact clean source checkout and helper against the claimed commit;
it does not re-resolve a moving published ref after acceptance, fetch, checkout
another commit, or relax template/configuration/what-if verification.
It conditionally creates
runs/<run_id>.worker.json and persists child-deployment/ownership evidence.
Automatic CI re-runs encounter this one-shot record and cannot repeat writes.
The coordinator requires BOTH exact remote completion and a matching successful
worker receipt before releasing locks or reporting success.

Complete owned resource-group deletion: arm-provider-closure-v1
----------------------------------------------------------------
Use deletion.inventory_mode="arm-provider-closure-v1", set every reviewed
resource_group.delete and resource.delete true, and add:
  deletion.closure: output of collect_resource_closure(cloud, exact_rg_ids)[0]
  deletion.closure_hash: SHA256(canonical closure)
  resource_group.owner: exact {factory_id,scaleset_id}

Read-only preparation convenience:
  freeze_deletion_inventory(cloud, draft_manifest, ownership_records_by_id)
This collects full closure, uses actual ownership tags where present and
requires verified deployment-receipt records for untaggable children. It
extracts cross-RG ARM references from live bodies; runtime rechecks those
references against declared dependencies. Retained external resource
dependencies must be covered by common_dependencies locks, never deleted.

The collector returns (fingerprint_closure, in-memory_resource_bodies).
It fully pages RG resources; fingerprints registered provider schemas; walks
every registered direct child collection recursively; and enumerates scoped
role/deny assignments, locks, policy assignments/exemptions and diagnostic settings.
Resource-group activity-log routing is subscription-scoped, not a diagnostic
settings child of the resource group; that explicit non-applicability is
recorded in closure. Resource-level diagnostic settings are enumerated.
Inherited authorization entries are excluded by actual scope, not name.
Storage service/default singletons are read explicitly. Key Vault accessPolicy
operations are inline parent properties, covered by the parent fingerprint.
Only explicit authoritative unsupported-extension error codes establish
non-applicability; a generic 404, missing permission, unsupported child list
endpoint or incomplete result blocks deletion.

Every discovered root, nested and extension resource must appear exactly once
in deletion.resources with its full body_hash, observed ETag/API version,
explicit owner and depends_on resource IDs. Names and region are never
ownership evidence. Tagged resources require exact ownership tags. Untaggable
children require:
  ownership_source: deployment-receipt
  ownership_evidence:
    run_id: UUID of a previously verified scoped worker deployment
    receipt_hash: SHA256(canonical persisted successful worker receipt)
The live storage receipt must explicitly list that exact resource/owner.
Its recorded full body fingerprint must still match the current instance;
out-of-band updates or a replaced resource require ownership reconciliation,
not blind acceptance of an old resource ID.
Unknown/adopted-by-name children cannot be invented into this ledger.

Complete provider/child/extension closure and ownership are re-read under the
leases before EACH RG delete. Cross-RG resource dependencies determine group
deletion order; cyclic dependencies block rather than guessing. Azure performs
the authorized group's internal dependency-aware cascade. The exact group
and every approved descendant must subsequently return 404. Failures retain
partial receipts and all physical locks. No external hub/shared group or
unrelated child is authorized. Soft-deleted data is not purged by this adapter.
Managed-resource-group/node-RG cascades must also be explicitly listed, owned
and locked. An implicit cascade to an external/unlisted managed group blocks
before mutation. Already-authorized cascaded groups are individually verified
absent and recorded; they are not blindly deleted again.
For an untagged managed RG, preparation may record
ownership_source="managed-parent" and managed_parent_id only when both live
links agree: RG.managedBy points to an owned, allowlisted managed-service
resource, and that resource explicitly names this RG as its managed/node RG.
Every child still requires independently verified ownership. A name or a
one-way managedBy string alone is insufficient. The preparation helper
discovers and validates this evidence; conflicting ownership tags block.

This protocol supports full owned factory RG sets, not arbitrary Azure
resource universes: an unenumerable/custom child or extension needs an audited
collector before execution. Never claim incomplete provider inventory is
complete merely because the parent RG has an ownership tag.

Backend orchestration and compatibility
---------------------------------------
One manifest executes one explicit scaleset/environment. Whole-factory deletion
MUST use capability factory_cohort="physical-lease-cohort-v1" and one call:

  execute_cohort(documents, source_root, execution_root, receipt_path)

The optional cloud_factory=Cloud and lock_factory=BlobLocks arguments are
dependency injection for offline tests, not manifest-controlled privileges.
The backend decrypts the whole protected DPAPI JSON and independently verifies
each expected manifest hash before passing the document list. No parent run ID
is needed. Keep the complete protected catalog authority until the aggregate
and every child receipt verify success; never remove successful children from
the authoritative catalog on partial/uncertain cohort failure.

All children must be nonempty, immutable, unexpired delete manifests for the
same factory and exactly the same source commit/ref/version. Run IDs and writable
physical RG scopes must be unique. Every child must use the complete owned-group
closure contract and authorize deletion of every inventoried RG/resource.
Different environments, subscriptions and ADO/GHA writers are supported.
Each target identity is independently verified against its existing tenant/
subscription/principal session; no login or account switch is attempted.
Disjoint tenants/stores are supported with those explicit sessions/access.
Shared physical scopes require the SAME authoritative account/container AND
enrollment blob/hash/revision. Shared scopes spanning target tenants currently
block with cohort-shared-scope-cross-tenant-auth-unsupported; configure a
supported explicit authentication/coordination topology instead of assuming
cross-tenant token access. Source must be an exact separate published checkout.

The runtime validates all input first, acquires the FULL UNION of physical RG
and common-dependency leases in globally sorted lowercase ARM-ID order, verifies
ALL live inventories/ownership/identities/enrollments and active-run exclusions,
then durably claims every child while ALL consent windows remain current.
No ARM mutation occurs until every claim has been verified. Shared scopes use
one lease, not repeated acquisitions. Cohort execution owns the union; prepared
inherited_leases are not accepted for this API. No manifest fields or lease IDs
are inserted into/rewritten in the approved children.

Child order is reverse dependency order across reviewed resource references and
enrolled common dependencies, with manifest-hash sorting for independent peers.
Duplicate writable scopes and cyclic dependencies block before mutations.
Every child uses its original claim under an internal inherited union lease
guard; all union leases/enrollments and frozen documents are checked throughout,
including when later children run past their original consent deadlines.
Within each child the existing per-resource closure, ownership and deletion
verification remains unchanged. RG absence polling allows up to 1440 five-second
polls (two hours); leaf polling remains 120 polls. This bounded operational
timeout is independent of consent expiry; an unverified timeout retains leases.

Before claiming, a confirmed failure releases acquired leases. Once any claim
is attempted, partial/uncertain failures conservatively retain the ENTIRE union,
all child receipts and the aggregate, with no retry, lease break or catalog
collapse. Success persists every child's verified completion before releasing
the union once. Failed releases report only still-retained scopes and require
reconciliation, never success. One-shot child claims prevent cross-machine replay.

Aggregate result and aggregate JSON at receipt_path:
  {
    "schema": 1, "operation": "delete-factory",
    "cohort_hash": SHA256(canonical(sorted(child_manifest_hash_strings))),
    "factory_id": "<factory>", "source_commit": "<40-hex>",
    "source_ref": "refs/tags/<reviewed-version>",
    "status": "succeeded" | "blocked" | "reconciliation-required",
    "mutation_started": true | false,
    "lock_retained": true | false, "locks_retained": ["<lowercase-physical-RG-ID>"],
    "started_at": "<ISO>", "updated_at": "<ISO>", "finished_at": "<ISO>",
    "error_code": "<stable-code, present only on failure>",
    "children": [ <child receipts in deterministic dependency-safe order> ]
  }
Each child preserves the existing receipt fields schema/run_id/manifest_hash/
manifest_revision/operation/target/source_commit/status/mutation_started/
deleted_resources, adding source_ref, cohort_hash, lock_retained, union-wide
locks_retained and its immutable execution_claim when accepted. Pending deletion
evidence and error_code are preserved on failure. Child receipts are written to
<execution_root>/<run_id>.receipt.json and existing runs/<run_id>.json blobs;
the immutable acceptance evidence is runs/<run_id>.claim.json. As with execute,
malformed/expired/mixed input or invalid execution paths can raise Blocked before
an execution directory exists; operational failures return the persisted result.
Aggregate and child files contain no configuration, bearer tokens or lease IDs.

Creation sequencing remains backend-owned. Existing single-target execute keeps
its signature and receipt semantics, including optional reviewed inherited
physical leases; a child never releases inherited leases and reports them in
parent_locks_retained. Those leases alone do not authorize expired input.
Whole-factory deletion must not be simulated by sequential independently
accepted execute calls or a local factory mutex.
Cloning none/all projects remains local independent-draft catalog work.
Creation never fabricates project001, or materializes catalog state as root
deployment files. All non-deployment/metadata settings remain in the frozen
config hash and must be explicitly accounted for by preparation.

Legacy reviewed ADO project contract=1 remains supported without a deployment
plan on non-shared remotes. Legacy GHA/root-global bootstrap is not used as a
fallback. Old published versions lacking these new templates, compiler/runtime
contracts, complete manifests or actual namespaced auth setup remain blocked.
The executing adapter must itself exactly match the helper published at the
selected source commit; a dirty/untracked copied helper cannot manufacture
capability support in an older release.
